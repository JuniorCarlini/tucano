Tucano

Date picker, select com busca e color picker para formulários. Sem dependências em runtime. Estilos escritos em Tailwind e distribuídos já compilados — o projeto que consome não precisa de build.

15 KB JS gzip 4 KB CSS gzip 0 dependências Sem preflight do Tailwind Pronto para toque Upload com progresso Toast e tooltip

Instalação

Dois arquivos e nada mais. Funciona com HTML puro, sem npm e sem build.

<!-- CDN -->
<link rel="stylesheet" href="https://cdn.jsdelivr.net/gh/JuniorCarlini/tucano@v0.9.6/dist/tucano.min.css">
<script src="https://cdn.jsdelivr.net/gh/JuniorCarlini/tucano@v0.9.6/dist/tucano.min.js" defer></script>

npm

npm install tucano
import { DatePicker, Select, ColorPicker } from 'tucano';
import 'tucano/css';
Prenda a versão. @latest no jsDelivr fica muito tempo em cache e serve build antigo sem avisar.

Depois disso, qualquer elemento com data-tuc-* é inicializado sozinho — inclusive o que chegar depois por swap do HTMX.

Date picker

Data, período, hora e data+hora. Campo com máscara, calendário navegável por mês e ano, e um painel que se adapta ao toque no celular.

Como usar

<input type="text" name="data" data-tuc-datepicker>
<input type="text" name="quando" data-tuc-datepicker data-time="true">
<input type="text" name="exato" data-tuc-datepicker data-time="true" data-minute-step="1">  <!-- minutos 00–59 -->
<input type="text" name="periodo" data-tuc-datepicker data-mode="range">

Opções que não cabem em atributo — disabledDates, presets próprios, onChange — vão pela API.

No celular o painel é o mesmo do desktop, adaptado ao toque: texto de 16px (abaixo disso o Safari do iOS dá zoom sozinho ao focar o campo), células maiores e, no modo período, os dois meses empilhados. O seletor do sistema continua disponível com data-native="true" — ele não altera o type do seu input, então o estilo do campo é preservado.

Select

Enriquece um <select> nativo. O elemento original continua no DOM guardando o valor, então name, multiple e required seguem funcionando.

Como usar

<select name="uf" data-tuc-select>
  <option value="">Selecione...</option>   <!-- vira placeholder -->
  <option value="SP">São Paulo</option>
</select>

<select name="tags" data-tuc-select multiple data-placeholder="Adicione...">
A busca ignora acentos: sao encontra "São Paulo". O campo tem altura fixa e linha única de propósito — com tags quebrando linha ele cresceria e desalinharia o formulário. O excesso rola na horizontal.

Busca no servidor

Para listas grandes demais para carregar inteiras. A cada digitação o componente pergunta ao servidor em vez de filtrar o que já está na página.

<select name="cliente" data-tuc-select data-url="{% url 'api-clientes' %}"></select>
def clientes(request):
    q = request.GET.get("q", "")
    qs = Cliente.objects.filter(nome__icontains=q)[:20]
    return JsonResponse([{"value": c.pk, "label": c.nome} for c in qs], safe=False)
AtributoPadrãoO que faz
data-url—Liga a busca no servidor
data-query-paramqNome do parâmetro na URL
data-min-chars1Caracteres antes de perguntar
data-debounce300Espera, em ms, antes de pedir
Aceita a resposta em vários formatos para o servidor não ter que mudar por causa daqui: [{value,label}], ["a","b"], {results:[...]} do DRF e {id,text} do Select2.
Por que não HTMX aqui. A lista vive dentro do popover que o componente redesenha. Se o HTMX também escrevesse ali, seriam dois donos do mesmo DOM — a mesma classe de conflito que fazia o calendário engolir cliques. E para uma lista de opções, JSON é o contrato certo: HTML teria que ser reinterpretado de volta em objetos. Para controle total existe loadOptions, que aceita qualquer origem.

Color picker

Área HSV, matiz, opacidade, paleta e conta-gotas. Aceita hex de 3, 4, 6 e 8 dígitos, rgb(), rgba(), hsl() e hsla().

Como usar

<input type="text" name="cor" value="#4f46e5" data-tuc-color>
<input type="text" name="marca" data-tuc-color data-alpha="false"
       data-swatches="#0a0a0a,#ea580c,#16a34a">
O estado interno é HSVA, não RGB: converter a cada movimento perderia a matiz quando a saturação chega a zero — todo cinza viraria vermelho ao clarear.

Upload

Arrastar e soltar, miniatura, validação de tipo e tamanho. O <input type="file"> continua no DOM, então name e required seguem valendo.

Os dois lugares

O modo é decidido pela presença de data-url, e a diferença não é só técnica: muda onde o upload vive.

No formulárioDireto
Quando sobeNo submitAo soltar o arquivo
O servidor receberequest.FILESUm POST por arquivo
O formulário postaOs arquivosSó os ids devolvidos
Progresso por arquivonãosim
Cancelar e repetirnãosim
Precisa de endpointnãosim
Funciona sem <form>nãosim
Por que não há progresso no modo formulário. Num submit comum o navegador envia tudo num bloco só e não reporta o andamento — não é uma limitação nossa, é como o HTML funciona. Progresso por arquivo exige que cada um suba na hora, que é o modo direto.

Como usar

<!-- No formulário: nada muda na sua view -->
<input type="file" name="anexos" multiple data-tuc-upload data-max-size="5mb">

<!-- Direto: sobe na hora, o form posta os ids -->
<input type="file" name="fotos" multiple accept="image/*"
       data-tuc-upload data-url="{% url 'upload-temp' %}">

No Django

# O modo direto precisa de um endpoint que devolva JSON com um id.
def upload_temp(request):
    arquivo = request.FILES["file"]
    temp = TempUpload.objects.create(arquivo=arquivo)
    return JsonResponse({"id": str(temp.id), "url": temp.arquivo.url})
O token CSRF é lido do cookie e enviado em X-CSRFToken sozinho. E lembre da limpeza: se a pessoa sobe arquivos e fecha a aba sem salvar, eles ficaram no servidor — uma tarefa apagando temporários com mais de 24h resolve.

Tipos aceitos

accept e multiple são os atributos nativos do input — o componente respeita os dois. O accept filtra a janela do sistema e é revalidado ao arrastar, onde o sistema não filtra.

<!-- por extensão -->
<input type="file" accept=".pdf,.docx" data-tuc-upload>

<!-- por família -->
<input type="file" accept="image/*" data-tuc-upload>

<!-- por tipo exato -->
<input type="file" accept="image/png,image/jpeg" data-tuc-upload>

<!-- misturando -->
<input type="file" accept=".pdf,image/*" multiple data-tuc-upload>
Prefira extensão a tipo MIME. O navegador nem sempre sabe o tipo de um arquivo: um .csv costuma chegar com type vazio, e aí accept="text/csv" recusa enquanto accept=".csv" aceita. Vale para .csv, .md, .log e formatos menos comuns. Para imagem e PDF, o MIME é confiável.

A dica embaixo da zona é gerada do próprio accept, junto com o limite de tamanho — você não precisa escrever de novo.

Máscaras

Formata enquanto se digita, valida documento e esconde dado sensível. O componente não envolve nem substitui o seu input — é comportamento puro, então o estilo que você já aplica continua valendo.

Campo sensível

Nasce oculto quando já tem conteúdo, mostrando só o final. O valor real vai num <input type="hidden"> com o mesmo name, então o servidor recebe o dado completo — o que fica escondido é só a tela.

Modos de esconder

ModoQuando usarResultado
fim (padrão)Documento, cartão, conta, telefone•••• •••• •••• 1234

<input data-tuc-reveal>                        <!-- fim, 2 caracteres -->
<input data-tuc-reveal data-reveal-visible="4">  <!-- fim, 4 caracteres -->
<input data-tuc-reveal="tudo">                 <!-- esconde tudo -->
<input type="email" data-tuc-reveal>          <!-- guarda o domínio -->
O e-mail esconde ao contrário do resto de propósito: o domínio é o que ajuda a reconhecer a conta, a parte local é o que identifica a pessoa. Guardar o fim, como no padrão, revelaria om.br e esconderia o útil. Sem @, ele esconde tudo — o padrão seguro.
Por que isso importa. Print de tela, gravação em suporte, alguém olhando por cima do ombro — o dado completo aparece sem ninguém pedir. Nascer oculto é a diferença entre expor por padrão e expor por escolha.

Sobre o CNPJ alfanumérico. O formato novo mantém as 14 posições e a mesma máscara: as 12 primeiras aceitam letras, as 2 últimas seguem numéricas, e o dígito verificador usa o código ASCII menos 48. Validação

Com data-validate, o dígito verificador é conferido ao sair do campo e o navegador barra o submit sozinho, via setCustomValidity — sem você escrever nada.

<input name="cpf" data-tuc-mask="cpf" data-validate="true">
<input name="cpf_cadastro" data-tuc-mask="cpf" data-tuc-reveal>
<input name="valor" data-tuc-mask="real">

Pela API: Tucano.mask.validarCPF(), validarCNPJ(), formatar(valor, 'cpf'). E a instância expõe getRaw() e getNumber().

Botão

Nasceu do que os componentes precisavam por dentro — o "Desfazer" do toast, o "Aplicar" do calendário. Em vez de cada um inventar o seu, sai tudo daqui, e fica disponível para o seu projeto também.

Variantes
Tamanhos 
<button class="tuc-btn is-primary">Salvar</button>
<button class="tuc-btn is-outline is-sm">Cancelar</button>
<button class="tuc-btn is-ghost is-icon" aria-label="Fechar">…</button>
ClassePara quê
is-primaryAção principal, na cor de destaque
is-outlineAção secundária, com borda
is-ghostTerciária, sem peso visual
is-dangerDestrutiva

Desabilitado mostra o cursor de bloqueio — nada de pointer-events: none, que impediria o elemento de receber o ponteiro e deixaria a pessoa sem sinal nenhum de que o botão não responde. Num <button disabled> o navegador já impede o clique sozinho. Com aria-disabled o clique continua chegando de propósito: é o caso de um botão que segue focável e anunciado, e quem usa o atributo trata o clique.
Não é um componente com JavaScript — é só classe. Um <button> continua sendo um <button>, com o type, o disabled e o foco do navegador. Altura e raio saem de --tuc-control-height e --tuc-radius-md, os mesmos dos campos.

Toast

Aviso que aparece num canto e some sozinho. Empilha, pausa quando o ponteiro entra e é anunciado por leitor de tela.

Experimente

Pelo código

Tucano.toast('Salvo');
Tucano.toast.erro('Não foi possível salvar');
Tucano.toast({
  type: 'sucesso',
  title: 'Contrato excluído',
  text: 'Ainda dá para voltar atrás.',
  action: { text: 'Desfazer', onClick: () => restaurar() },
  position: 'bottom-end',   // top-start|top-center|top-end|bottom-*
  duration: null,           // não some sozinho
});

Com o Django, sem escrever JavaScript

As mensagens do framework de messages viram toast direto:

{% for m in messages %}
  <div data-tuc-toast data-type="{{ m.tags }}">{{ m }}</div>
{% endfor %}

debug, info, success, warning e error do Django são traduzidos sozinhos.

Com o HTMX, disparado pelo servidor

return HttpResponse(headers={
    "HX-Trigger": json.dumps({"tucano:toast": {
        "type": "sucesso", "text": "Contrato salvo",
    }})
})
Um detalhe que quase toda biblioteca erra. O aria-live fica no container, criado antes de qualquer mensagem — se a região nascer junto com o texto, o leitor de tela não anuncia. Erro vai para uma região assertive separada; o resto, polite.
O relógio pausa quando o ponteiro entra ou algo dentro recebe foco. Sem isso, o aviso some no instante em que a pessoa vai clicar no "Desfazer".

Tooltip

Dica curta ancorada num elemento. Aparece no ponteiro e no foco do teclado, e responde ao toque no celular.

Aponte, ou navegue com Tab 
<button data-tuc-tip="Gera o PDF com o layout atual">Exportar</button>
<button data-tuc-tip="..." data-placement="bottom-center" data-delay="600">
No celular não existe hover. Tooltip que só escuta mouseover simplesmente nunca aparece no telefone — por isso aqui o toque abre e o toque fora fecha. E Escape fecha mesmo com o ponteiro parado em cima, como pede a WCAG 1.4.13.
O texto sai do aria-describedby, então o leitor de tela lê a dica junto com o botão. Um title é aproveitado quando o elemento tem data-tuc-tip vazio — e removido, senão a dica nativa do navegador apareceria por cima da nossa. Sem o atributo, nada é tocado: sequestrar todo title da página seria intrusivo demais para uma biblioteca.

## Campos de formulário

Este projeto usa a Tucano para data, período, select com busca e cor.
Não escreva esses componentes do zero.

Referência completa: https://juniorcarlini.github.io/tucano/llms.txt

Não remova o name do input nem o <select> nativo: é neles que o valor vive.
