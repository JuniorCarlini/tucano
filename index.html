Tucano

Formulário, listagem e diálogo para quem escreve HTML e não quer arrastar um framework junto. Sem dependências em runtime. Estilos escritos em Tailwind e distribuídos já compilados — o projeto que consome não precisa de build.

36 KB JS gzip 11 KB CSS gzip 0 dependências Sem preflight do Tailwind Pronto para toque Acessível por teclado Pensado para Django

Instalação

Dois arquivos e nada mais. Funciona com HTML puro, sem npm e sem build.

<!-- CDN -->
<link rel="stylesheet" href="https://cdn.jsdelivr.net/gh/JuniorCarlini/tucano@v0.30.2/dist/tucano.min.css">
<script src="https://cdn.jsdelivr.net/gh/JuniorCarlini/tucano@v0.30.2/dist/tucano.min.js" defer></script>

npm

npm install tucano
import { DatePicker, Select, ColorPicker, Upload, Mask, toast, modal } from 'tucano';
import 'tucano/css';
Prenda a versão. @latest no jsDelivr fica muito tempo em cache e serve build antigo sem avisar.

Depois disso, qualquer elemento com data-tuc-* é inicializado sozinho — inclusive o que chegar depois por swap do HTMX.

Date picker

Data, período, hora e data+hora. Campo com máscara, calendário navegável por mês e ano, e um painel que se adapta ao toque no celular.

Como usar

<input type="text" name="date" data-tuc-datepicker>
<input type="text" name="quando" data-tuc-datepicker data-time="true">
<input type="text" name="exato" data-tuc-datepicker data-time="true" data-minute-step="1">  <!-- minutos 00–59 -->
<input type="text" name="periodo" data-tuc-datepicker data-mode="range">

Opções que não cabem em atributo — disabledDates, presets próprios, onChange — vão pela API.

No celular o painel é o mesmo do desktop, adaptado ao toque: texto de 16px (abaixo disso o Safari do iOS dá zoom sozinho ao focar o campo), células maiores e, no modo período, os dois meses empilhados. O seletor do sistema continua disponível com data-native="true" — ele não altera o type do seu input, então o estilo do campo é preservado.

Select

Enriquece um <select> nativo. O elemento original continua no DOM guardando o valor, então name, multiple e required seguem funcionando.

Como usar

<select name="uf" data-tuc-select>
  <option value="">Selecione...</option>   <!-- vira placeholder -->
  <option value="SP">São Paulo</option>
</select>

<select name="tags" data-tuc-select multiple data-placeholder="Adicione...">
A busca ignora acentos: sao encontra "São Paulo". O campo tem altura fixa e linha única de propósito — com tags quebrando linha ele cresceria e desalinharia o formulário. O excesso rola na horizontal.

Busca no servidor

Para listas grandes demais para carregar inteiras. A cada digitação o componente pergunta ao servidor em vez de filtrar o que já está na página.

<select name="cliente" data-tuc-select data-url="{% url 'api-clientes' %}"></select>
def clientes(request):
    q = request.GET.get("q", "")
    qs = Cliente.objects.filter(nome__icontains=q)[:20]
    return JsonResponse([{"value": c.pk, "label": c.name} for c in qs], safe=False)
AtributoPadrãoO que faz
data-url—Liga a busca no servidor
data-query-paramqNome do parâmetro na URL
data-min-chars1Caracteres antes de perguntar
data-debounce300Espera, em ms, antes de pedir
Aceita a resposta em vários formatos para o servidor não ter que mudar por causa daqui: [{value,label}], ["a","b"], {results:[...]} do DRF e {id,text} do Select2.
Por que não HTMX aqui. A lista vive dentro do popover que o componente redesenha. Se o HTMX também escrevesse ali, seriam dois donos do mesmo DOM — a mesma classe de conflito que fazia o calendário engolir cliques. E para uma lista de opções, JSON é o contrato certo: HTML teria que ser reinterpretado de volta em objetos. Para controle total existe loadOptions, que aceita qualquer origem.

Color picker

Área HSV, matiz, opacidade, paleta e conta-gotas. Aceita hex de 3, 4, 6 e 8 dígitos, rgb(), rgba(), hsl() e hsla().

Como usar

<input type="text" name="color" value="#4f46e5" data-tuc-color>
<input type="text" name="mark" data-tuc-color data-alpha="false"
       data-swatches="#0a0a0a,#ea580c,#16a34a">
O estado interno é HSVA, não RGB: converter a cada movimento perderia a matiz quando a saturação chega a zero — todo cinza viraria vermelho ao clarear.

Upload

Arrastar e soltar, miniatura, validação de tipo e tamanho. O <input type="file"> continua no DOM, então name e required seguem valendo.

Os dois lugares

O modo é decidido pela presença de data-url, e a diferença não é só técnica: muda onde o upload vive.

No formulárioDireto
Quando sobeNo submitAo soltar o arquivo
O servidor receberequest.FILESUm POST por arquivo
O formulário postaOs arquivosSó os ids devolvidos
Progresso por arquivonãosim
Cancelar e repetirnãosim
Precisa de endpointnãosim
Funciona sem <form>nãosim
Por que não há progresso no modo formulário. Num submit comum o navegador envia tudo num bloco só e não reporta o andamento — não é uma limitação nossa, é como o HTML funciona. Progresso por arquivo exige que cada um suba na hora, que é o modo direto.

Como usar

<!-- No formulário: nada muda na sua view -->
<input type="file" name="anexos" multiple data-tuc-upload data-max-size="5mb">

<!-- Direto: sobe na time, o form posta os ids -->
<input type="file" name="fotos" multiple accept="image/*"
       data-tuc-upload data-url="{% url 'upload-temp' %}">

No Django

# O mode direct precisa de um endpoint que devolva JSON com um id.
def upload_temp(request):
    file = request.FILES["file"]
    temp = TempUpload.objects.create(file=file)
    return JsonResponse({"id": str(temp.id), "url": temp.file.url})
O token CSRF é lido do cookie e enviado em X-CSRFToken sozinho. E lembre da limpeza: se a pessoa sobe arquivos e fecha a aba sem salvar, eles ficaram no servidor — uma tarefa apagando temporários com mais de 24h resolve.

Tipos aceitos

accept e multiple são os atributos nativos do input — o componente respeita os dois. O accept filtra a janela do sistema e é revalidado ao arrastar, onde o sistema não filtra.

<!-- por extensão -->
<input type="file" accept=".pdf,.docx" data-tuc-upload>

<!-- por família -->
<input type="file" accept="image/*" data-tuc-upload>

<!-- por type exato -->
<input type="file" accept="image/png,image/jpeg" data-tuc-upload>

<!-- misturando -->
<input type="file" accept=".pdf,image/*" multiple data-tuc-upload>
Prefira extensão a tipo MIME. O navegador nem sempre sabe o tipo de um arquivo: um .csv costuma chegar com type vazio, e aí accept="text/csv" recusa enquanto accept=".csv" aceita. Vale para .csv, .md, .log e formatos menos comuns. Para imagem e PDF, o MIME é confiável.

A dica embaixo da zona é gerada do próprio accept, junto com o limite de tamanho — você não precisa escrever de novo.

Máscaras

Formata enquanto se digita, valida documento e esconde dado sensível. O componente não envolve nem substitui o seu input — é comportamento puro, então o estilo que você já aplica continua valendo.

Campo sensível

Nasce oculto quando já tem conteúdo, mostrando só o final. O valor real vai num <input type="hidden"> com o mesmo name, então o servidor recebe o dado completo — o que fica escondido é só a tela.

<input data-tuc-reveal>                        <!-- fim, 2 chars -->
<input data-tuc-reveal data-reveal-visible="4">  <!-- fim, 4 chars -->
<input data-tuc-reveal="tudo">                 <!-- esconde tudo -->

O e-mail esconde ao contrário do resto de propósito: o domínio é o que ajuda a reconhecer a conta, a parte local é o que identifica a pessoa. Guardar o fim, como no padrão, revelaria om.br e esconderia o útil. Sem @, ele esconde tudo — o padrão seguro.
Por que isso importa. Print de tela, gravação em suporte, alguém olhando por cima do ombro — o dado completo aparece sem ninguém pedir. Nascer oculto é a diferença entre expor por padrão e expor por escolha.

Validação

Com data-validate, o dígito verificador é conferido ao sair do campo e o navegador barra o submit sozinho, via setCustomValidity — sem você escrever nada.

<input name="cpf" data-tuc-mask="cpf" data-validate="true">
<input name="cpf_cadastro" data-tuc-mask="cpf" data-tuc-reveal>
<input name="value" data-tuc-mask="real">

Pela API: Tucano.mask.validateCPF(), validateCNPJ(), format(value, 'cpf'). E a instância expõe getRaw() e getNumber().

Botão

Nasceu do que os componentes precisavam por dentro — o "Desfazer" do toast, o "Aplicar" do calendário. Em vez de cada um inventar o seu, sai tudo daqui, e fica disponível para o seu projeto também.

Variantes
Tamanhos 
<button class="tuc-btn is-primary">Salvar</button>
<button class="tuc-btn is-outline is-sm">Cancelar</button>
<button class="tuc-btn is-ghost is-icon" aria-label="Fechar">…</button>
ClassePara quê
is-primaryAção principal, na cor de destaque
is-outlineAção secundária, com borda
is-ghostTerciária, sem peso visual
is-dangerDestrutiva

Desabilitado mostra o cursor de bloqueio — nada de pointer-events: none, que impediria o elemento de receber o ponteiro e deixaria a pessoa sem sinal nenhum de que o botão não responde. Num <button disabled> o navegador já impede o clique sozinho. Com aria-disabled o clique continua chegando de propósito: é o caso de um botão que segue focável e anunciado, e quem usa o atributo trata o clique.
Não é um componente com JavaScript — é só classe. Um <button> continua sendo um <button>, com o type, o disabled e o foco do navegador. Altura e raio saem de --tuc-control-height e --tuc-radius-md, os mesmos dos campos.

Toast

Aviso que aparece num canto e some sozinho. Empilha, pausa quando o ponteiro entra e é anunciado por leitor de tela.

Posição
Experimente

Pelo código

Tucano.toast('Salvo');
Tucano.toast.error('Não foi possível salvar');
Tucano.toast({
  type: 'success',
  title: 'Contrato excluído',
  text: 'Ainda dá para voltar atrás.',
  action: { text: 'Desfazer', onClick: () => restaurar() },
  position: 'bottom-end',   // padrão. top-start|top-center|top-end|bottom-*
  duration: null,           // não some sozinho
});

Carregando, e o fim da operação no mesmo cartão

O toast de loading não some sozinho — quem o encerra é o fim da operação. Com promise() ele vira sucesso ou erro no mesmo cartão, em vez de fechar um e abrir outro no lugar.

// control manual: guarda a instância e vira o que precisar
const t = Tucano.toast.loading('Enviando arquivo...');
await enviar();
t.update({ type: 'success', text: 'Arquivo enviado' });

// ou entrega a promise e deixa ela cuidar dos três estados
Tucano.toast.promise(fetch(url), {
  loading: 'Enviando file...',
  success: (r) => `Enviado (${r.status})`,
  error: 'Não deu para enviar',
});

Ao virar error o toast troca de live region, então o leitor de tela anuncia a mudança — e nada se desloca na tela, porque a posição vem da pilha e não da região.

Com o Django, sem escrever JavaScript

As mensagens do framework de messages viram toast direto:

{% for m in messages %}
  <div data-tuc-toast data-type="{{ m.tags }}">{{ m }}</div>
{% endfor %}

debug, info, success, warning e error do Django são traduzidos sozinhos.

Com o HTMX, disparado pelo servidor

return HttpResponse(headers={
    "HX-Trigger": json.dumps({"tucano:toast": {
        "type": "success", "text": "Contrato salvo",
    }})
})
Um detalhe que quase toda biblioteca erra. O aria-live fica no container, criado antes de qualquer mensagem — se a região nascer junto com o texto, o leitor de tela não anuncia. Erro vai para uma região assertive separada; o resto, polite.
O relógio pausa quando o ponteiro entra ou algo dentro recebe foco. Sem isso, o aviso some no instante em que a pessoa vai clicar no "Desfazer".

Tooltip

Dica curta ancorada num elemento. Aparece no ponteiro e no foco do teclado, e responde ao toque no celular.

Lados — as quatro do shadcn, com flip quando não cabe
Alinhamento no eixo — start, center, end
Cor
Outros 
<button data-tuc-tip="Gera o PDF com o layout current">Exportar</button>
<button data-tuc-tip="..." data-placement="right-center" data-delay="600">
<button data-tuc-tip="..." data-tip-class="tip-roxo">

Lados: top, right, bottom, left; alinhamentos start, center, end — as mesmas do shadcn, e o padrão também é o dele, top-center. Quando o lado pedido não cabe, a dica vira para o oposto e a seta acompanha.

Trocar a cor

Duas variáveis, e a seta acompanha sozinha. Vale global, no .tuc-tip, ou num caso só, com data-tip-class:

.tip-roxo { --tuc-tip-bg: #4f46e5; --tuc-tip-fg: #fff; }
No celular não existe hover. Tooltip que só escuta mouseover simplesmente nunca aparece no telefone — por isso aqui o toque abre e o toque fora fecha. E Escape fecha mesmo com o ponteiro parado em cima, como pede a WCAG 1.4.13.
O texto sai do aria-describedby, então o leitor de tela lê a dica junto com o botão. Um title é aproveitado quando o elemento tem data-tuc-tip vazio — e removido, senão a dica nativa do navegador apareceria por cima da nossa. Sem o atributo, nada é tocado: sequestrar todo title da página seria intrusivo demais para uma biblioteca.

Modal

Diálogo que se sobrepõe a tudo, com o fundo desfocado e um brilho da cor do tom. Feito sobre o <dialog> nativo.

Tamanhos
Tons — mudam o brilho do fundo e a aura da caixa
Comportamento

Escrito no HTML

Este <dialog> já estava na página. É o caminho para um form renderizado pelo servidor.

Pelo código

Tucano.modal({
  title: 'Excluir contrato',
  text: 'Esta ação não pode ser desfeita.',
  tone: 'danger',       // default | danger | success | warning
  size: 'md',       // sm | md | lg | full
  sheet: true,         // no mobile sobe do rodapé
  actions: [
    { text: 'Cancelar', variant: 'outline' },
    { text: 'Excluir', variant: 'danger', onClick: () => excluir() },
  ],
});

// confirmação como promise — o caso mais comum num CRUD
if (await Tucano.confirm({ title: 'Excluir contrato?' })) excluir();

Com o Django

Quando o conteúdo vem renderizado pelo servidor, o <dialog> mora no template e o Tucano só cuida de abrir, fechar e animar:

<dialog class="tuc-modal is-md" id="excluir">
  <div class="tuc-modal__panel">
    <form method="post">{% csrf_token %} ... </form>
    <button data-tuc-modal-close>Cancelar</button>
  </div>
</dialog>

<button data-tuc-modal="#excluir">Excluir</button>
Por que <dialog> e não uma div com z-index. O showModal() põe o elemento na top layer do navegador — acima de qualquer z-index, e imune a ancestral com overflow: hidden ou transform, que são justamente os três motivos de um modal artesanal aparecer cortado ou por baixo. Armadilha de foco, devolução do foco a quem abriu e Escape vêm junto, sem JavaScript nosso.

Acordeão

Blocos que recolhem e expandem. Feito sobre <details> nativo: funciona com teclado, é anunciado pelo leitor de tela e já abre e fecha antes de o JavaScript carregar.

Perguntas frequentes — um de cada vez, com data-single
Preciso de build no meu projeto?

Não. O CSS já vai compilado e o Tailwind é usado só aqui dentro. Do seu lado são dois arquivos e nada mais.

Funciona com HTMX?

Sim. O que chega por swap é inicializado sozinho, então campo novo vindo do servidor já nasce funcionando.

E se o JavaScript falhar?

Este acordeão continua abrindo e fechando: ele é <details> nativo. O que se perde é só a animação.

Com conteúdo de verdade dentro
Filtros do relatório
Colunas visíveis

Qualquer coisa cabe aqui — a altura é medida pelo navegador, não chutada por nós, então formulário, tabela e imagem funcionam igual.

O HTML é o de sempre

<div data-tuc-accordion data-single="true">
  <details open>
    <summary>Projetos</summary>
    <p>Listar, criar e acompanhar vistorias.</p>
  </details>
</div>
Por que <details>. Teclado, semântica e estado já vêm dele — e se o JavaScript falhar ou ainda não tiver carregado, o acordeão abre e fecha do mesmo jeito. O que o nativo não faz é animar: a altura do conteúdo é auto, que não transiciona, e ao fechar o navegador some com o conteúdo no mesmo quadro. A abertura resolvemos em CSS puro, animando uma linha de grid de 0fr a 1fr; o fechamento precisa de JavaScript, para o elemento seguir aberto enquanto encolhe.
Para menu lateral existe .tuc-accordion.is-plain, que tira as divisórias e deixa o título com cara de rótulo de grupo. Ele só faz sentido dentro de uma coluna estreita — veja o exemplo de menu, onde ele aparece no contexto para o qual foi feito.

As regras de aparência são as mesmas da área de edição, compartilhadas no CSS — os dois não têm como divergir. E o código publicado também é colorido, pelo init(), inclusive o que chegar depois por swap do HTMX.

Atalhos: Ctrl/Cmd+B, +I, +U e +K. Na tabela, Tab anda entre as células e, na última, cria uma linha nova — dá para preencher sem tirar as mãos do teclado.

Colar entra sempre como texto puro. É o que evita o HTML do Word e do Google Docs, com tabelas de layout e estilos embutidos, que é onde editor caseiro quebra primeiro. Você perde a formatação da origem e ganha um documento que continua sendo o seu.
A saída passa por uma peneira de tags a cada leitura. Só sobrevivem parágrafo, título, negrito, itálico, sublinhado, listas, citação, código, link e tabela. Atributo nenhum passa, exceto o href — e só se apontar para um destino aceitável, o que barra javascript:. É por aí que passariam onclick e onerror.

Ainda assim, sanitize no servidor antes de publicar. O HTML chega por POST e ninguém garante que veio deste editor.
O <textarea> original continua no DOM guardando o valor, então name, required e o POST funcionam sem mudar a sua view. Fora do escopo: mesclar células e redimensionar coluna — é o que faz editor virar projeto.

Montando em JS

Cada item aceita text, icon (o d de um path SVG), shortcut, href, onClick, variant e disabled. Sozinhos valem separator e label. Item com href vira <a> — o meio do botão continua abrindo em nova aba, e o menu não rouba o menu de contexto do navegador.

O foco entra e volta. Abrir leva o foco ao primeiro item, as setas andam entre eles, Home e End vão às pontas, e fechar devolve o foco ao gatilho. Os itens ficam com tabindex="-1" de propósito: quem navega dentro de um menu é a seta, não o Tab — deixá-los tabuláveis faria o Tab sair do menu um item por vez, que é justamente o que o padrão de menu evita.

A célula é livre

Dentro do <td> cabe o que você quiser. O que a biblioteca oferece são os arranjos que aparecem em toda listagem, para ninguém ter de reinventar o alinhamento de um avatar ao lado de um nome:

ClasseO que faz
.tuc-table__user + __avatar + __subFoto (ou iniciais), nome e uma segunda linha discreta. Para a segunda linha cortar com reticência em vez de esticar a tabela, dê largura à coluna: <th style="width:38%">
.tuc-badgeEtiqueta de estado — is-success, is-warning, is-danger, is-info
.tuc-table__actionsColuna encostada à direita. Dentro dela vão os botões do sistema — tuc-btn is-outline is-icon is-sm
.is-numberAlinha à direita com dígitos de largura fixa, para comparar valores com a vista
is-striped is-bordered is-compactVariantes da tabela inteira

Ordenação: data-sort aceita text, number, date e none. Quando o texto exibido não ordena bem — R$ 1.234,50, 12/09/2026 — use data-sort-value com o valor cru.

Ordenar é trabalho do servidor, e esse é o padrão. Numa lista paginada, reordenar as vinte linhas que estão na tela produz uma ordem falsa: o maior valor real pode estar na página 7, e a tabela passa a mentir com cara de verdade. Por isso o cabeçalho é um <a> apontando para a mesma URL com ?sort= e ?dir= — funciona sem JavaScript nenhum, funciona com hx-boost do HTMX, abre em outra aba, e a seta continua certa depois do recarregamento porque o estado sai da query string. Trocar a ordem também volta para a página 1: continuar na 7 com outra ordem mostraria um pedaço do meio de uma lista que ninguém viu.

Na sua view, ?sort e ?dir entram no order_by() antes do Paginator — que é exatamente onde a ordenação tem de acontecer. O exemplo acima usa data-sort-mode="client" só porque é uma demonstração sem servidor atrás; numa tabela pequena e completa, sem paginação, esse modo também é o certo.
A seleção continua sendo um formulário. Cada linha ganha um <input type="checkbox" name="selected" value="{{ data-id }}"> de verdade — no Django chega como request.POST.getlist('selected'), sem JavaScript no meio e funcionando com o botão de submit que você já tem.

Paginação

Feita para o Paginator do Django: você passa o número da página e o total, e ela monta o resto usando os mesmos botões do resto da biblioteca.

Muitas páginas — pontas, vizinhança e reticência
Poucas páginas — sem reticência, e a ponta inativa sai do caminho 
<div data-tuc-pagination
     data-page="{{ page_obj.number }}"
     data-pages="{{ page_obj.paginator.num_pages }}"></div>

Atributos: data-param (o nome na query string, padrão page), data-around e data-edges para quantos números aparecem ao redor da atual e nas pontas, data-prev-text e data-next-text. Alinhamento com is-center ou is-end.

Os itens são <a> com href de verdade, e são os mesmos .tuc-btn do resto da biblioteca — não há um segundo desenho de botão aqui. O link preserva o resto da query string, então filtro, busca e ordem não se perdem ao virar a página; e é isso que faz o botão do meio abrir em outra aba, o voltar do navegador funcionar e o buscador indexar. Quem precisa interceptar passa onChange e o clique é cancelado.
A ponta desativada é <span>, não <a> sem href: um link que não leva a lugar nenhum continua no caminho do Tab e é anunciado como link. E com uma página só a navegação inteira não é renderizada — não há para onde ir.

Modal e tooltip seguem a mesma regra:

TeclaModalTooltip

Chegar de Tab não abre nada. Quem tabula por um formulário para alcançar o botão de salvar não deveria levar um calendário na cara a cada campo, com o painel cobrindo o campo seguinte — é a regra do <select> nativo e do ARIA APG. Abrir é sempre explícito: ↓, Enter, Espaço ou o clique. No campo de cor o gatilho é a amostra ao lado, que é um <button> de verdade. Quem preferir o comportamento antigo no date picker liga openOnFocus: true.
O Enter no campo de data é do formulário, não nosso. Ele é um campo de texto dentro de um <form>, e Enter num campo de texto envia o formulário — é o que qualquer pessoa espera depois de digitar a data. Sequestrar a tecla para abrir o calendário quebraria o envio em silêncio em todo form que já existe, então ali quem abre é o Espaço. E ele só abre com o campo vazio: em modo com hora se digita 07/09/2026 14:30, e ali o espaço é digitação.
O Esc fechar o tooltip com o mouse ainda em cima não é detalhe: é o que a WCAG 1.4.13 pede, para quem usa ampliação de tela e precisa tirar da frente uma dica que cobre o conteúdo. E a armadilha de foco do modal vem do <dialog> nativo, não de JavaScript nosso.
